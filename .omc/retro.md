## 0. 결과 통보 요약

채용팀 피드백 핵심:

- 멀티 에이전트 구조의 체계적 설계, 문서화는 인정.
- 그러나 **"에이전트 간 상호작용을 얼마나 독립적이고 추상화된 구조로 설계했는지"**가 평가 중심이었는데, 제출물은 **orchestration 비중이 상대적으로 크게** 느껴졌다.
- **"에이전트 간 협업이나 상호작용 방식이 실제로 어떻게 발전해 나가는지"**가 제한적으로 드러났다.

## 2. 잘된 점 (계속할 것)

- **ralplan 2라운드까지 돌려 PRD를 인수기준 단위로 박제** — `.omc/prd.json` 10 스토리 모두 grep·exec 단위로 검증 가능. 진행 중 흔들림 없었음.
- **AGENTS.md 단일 진실 출처 박제** — ADR + JSONL 스키마 + UI 정책 한 파일. 코드와 어긋나면 문서를 먼저 고치는 룰 일관 유지.
- **HANDOFF.md 1페이지 평가 가이드 분리** — 채점자 진입 부하 줄이는 시도. 평가 결과와 무관하게 다음 외주 납품물에 동일 패턴 적용 가치.
- **시크릿 안전성 자동 검증** — `scrub-check.sh` CI 박제, JSONL/콘솔/SSE 어디에도 키 echo 없음. 외주에서도 그대로 쓸 가치 있음.

## 3. 안 됐던 점 (개선할 것)

### 3-1. **포지셔닝 오독** — 가장 치명적

- 가설로 박은 차별화: **"사용자가 토론에 끼어든다"** (인터럽트·Pause·Queue 4종).
- 평가자가 본 차별화: **"에이전트 자체의 자율성 / 협업 발전 양상"**.
- 베이글코드는 게임 AI 회사 — NPC·에이전트 emergent behavior가 본업이라는 사실을 견적 시점에 충분히 못 박았음. 사용자 개입은 **사람-AI 협업 도구** 관점이지 **AI-AI 협업 도구** 관점이 아니었다.
- **다음 적용**: 채용 과제는 _지원 회사의 본업 도메인_ 으로 차별화 가설을 세워야. 자기 강점(멀티에이전트 운영 통찰)을 과제 평가 축에 정렬시키는 것이 우선.

### 3-2. **에이전트 추상화 부족**

- AgentAdapter 인터페이스는 깔끔했지만, 어댑터는 사실상 **"orchestrator가 호출하는 SDK 래퍼"**에 가까웠다. 자율 행위자가 아니었다.
- 라운드 회전·인터럽트는 "메커니즘"이지 "협업 진화"가 아니다 — 라운드 N과 라운드 N+1에서 에이전트의 행동 양상이 _변화하지 않는다_. 역할 자가조정·합의 형성·갈등 해소 같은 emergent layer 부재.
- **다음 적용**: 멀티에이전트 도구 만들 땐 "에이전트가 다음 턴에 _무엇을_ 할지 스스로 결정하는 layer"가 있는지 자문. 없으면 그건 분기 호출이지 협업이 아님.

### 3-3. **polish 4시간이 평가에 전혀 기여 안 함**

- M9격 polish (CommandPalette·단축키·폰트·opencode 톤)에 4시간 투입. 채점자는 본편 시연 외 UI 폴리시는 본 흔적 없음.
- ralplan 통과한 PRD 10 스토리 외에 추가한 것 — _원래 박제한 우선순위 밖으로 넘어간 시간_.
- **다음 적용**: 견적·박제 후 확장은 위험. 마감 전 polish 시간이 남으면 _리스크 큰 평가 축_(이번 경우 에이전트 emergent behavior 시연)을 보강하는 데 써야 함.

### 3-4. **시연 녹화 미첨부 가능성**

- M8 본편 녹화는 했지만 평가자가 본 게 코드뿐인지 녹화도 본 건지 통보문에서 확인 불가. README/HANDOFF에 녹화 링크 박제가 약했을 수 있음.
- **다음 적용**: 채용 과제 제출 시 README 최상단에 녹화 링크 (≤30초 GIF 포함) 무조건 박제.
